### 4.1 Gradle wrapper integrity: **FAILED check, mitigated in CI** [VERIFIED]

| | SHA-256 |
|---|---|
| `MyUmrahJourney/gradle/wrapper/gradle-wrapper.jar` (as imported) | `7d3a4ac4de1c32b59bc6a4eb8ecb8e612ccd0cf1ae1e99f66902da64df296172` |
| Gradle's published wrapper jar checksum for 8.10 / 8.10.1 / **8.10.2** ([gradle.org/release-checksums](https://gradle.org/release-checksums/)) | `2db75c40782f5e8ba1fc278a5574bab070adccb2d21ca5a6e5ed840888448046` |

**They do not match.** The bundled jar is therefore not byte-identical to the official 8.10.2 wrapper. Its manifest also lacks `Implementation-Version`. Its origin is unknown; it may be a wrapper generated by a different Gradle release, which often works but cannot be trusted by checksum. (`gradle-wrapper.properties` also has no `distributionSha256Sum`.)

What I did, without touching the imported file:

- `tools/verify_gradle_wrapper.sh` runs first in the Codemagic build. If the jar mismatches, it downloads `gradle-8.10.2-bin.zip`, requires that download to match Gradle's published SHA-256 (`31c55713e40233a8303827ceb42ca48a47267a0ad4bab9177123121e71524c26`), generates a wrapper from that verified distribution, and replaces the jar **in the CI workspace only**, plus pins `distributionSha256Sum`.
- The replaced `gradle-wrapper.jar` and `gradle-wrapper.properties` are uploaded as build artifacts. After a successful build we can commit them deliberately (as its own documented commit) so the repository holds a verified wrapper.
- Tested locally: checksum-match path, mismatch path (it correctly fails cleanly when the download is blocked, and changes nothing), wrong-version path. **The restore path itself was NOT run end to end**, because this sandbox cannot reach `services.gradle.org`. Treat it as untested until the first Codemagic log.

I could not fetch the official jar myself: `raw.githubusercontent.com` and the Gradle distribution servers are blocked here.

- [VERIFIED] Versions: `gdx` and `gdx-backend-android` **1.12.1**, as declared in `gradle/libs.versions.toml`. Nothing was changed.
- [VERIFIED] The four native jars the project requests exist on Maven Central for 1.12.1: `gdx-platform-1.12.1-natives-armeabi-v7a.jar` (71,182 bytes), `-arm64-v8a` (75,731), `-x86` (85,887), `-x86_64` (87,213) ([listing](https://repo1.maven.org/maven2/com/badlogicgames/gdx/gdx-platform/1.12.1/)).
- [VERIFIED] The project's `copyGdxNatives` task (in `game/build.gradle.kts`) resolves these jars, reads the ABI from the file name, unpacks the `*.so` files at each jar's root into `game/build/generated/gdxNatives/<abi>/`, registers that folder as `jniLibs`, and is wired in before `preBuild` and every `merge*JniLibFolders` task.
- [ASSUMPTION] `libgdx.so` sits at each jar's root (libGDX's standard layout). I could not download a jar to open it. If wrong, the APK would build without `libgdx.so` and crash on launch.
- [NEW SAFEGUARD] After `:app:assembleDebug`, the Codemagic build **fails with a clear message if `lib/*/libgdx.so` is missing from the APK**, and prints a 16 KB alignment report (below).
- [ASSUMPTION] `project.copy {}` inside `doLast` is deprecated on Gradle 8.x but works on 8.10.2; it would need rewriting before any Gradle 9 upgrade.

### 4.4 16 KB page size: why I did **not** upgrade libGDX

The spec pins libGDX 1.12.1, and you asked for an explanation before any upgrade. Nothing was upgraded.

What is known:

- [VERIFIED, README] The Stage 2 README states that its 1.12.1 natives are **not** 16 KB page-aligned. [NOT VERIFIED] by me: I could not open the jars. **The first Codemagic build will measure it** (`elf-alignment-report.txt`).
- [VERIFIED from sources] libGDX's own PR for 16 KB support (#7394) was **not merged** into libGDX; the work was moved to the `gdx-jnigen` tool ([PR #7394](https://www.Github.com/libgdx/libgdx/pull/7394)). In the libGDX issue tracker ([#7695](https://github.com/libgdx/libgdx/issues/7695)) the status is **unsettled**: some users report 16 KB-aligned results with libGDX 1.13.1 and Android Studio 2025.1.3+/AGP 8.5.1+, others still see 4 KB; a maintainer says mixing 1.13.1 and 1.13.5 dependencies on Android is a problem and recommends 1.13.1 for Android. One user reports Google Play flagging an app and a 1 May 2026 deadline; **check Google's current policy directly** ([Android: Support 16 KB page sizes](https://developer.android.com/guide/practices/page-sizes)), I did not verify it.
- [VERIFIED] libGDX 1.14.0 exists (October 2025). Its release notes list only API breaking changes (`JsonSkimmer`, `StringBuilder` removed in favour of `CharArray`, `JsonValue#get` case-sensitivity, `Pools#get/obtain`) and say nothing about 16 KB ([1.14.0 notes](https://libgdx.com/news/2025/10/gdx-1-14-0)). Stage 2 uses none of those APIs (searched all 31 Kotlin files).

Implications:

| Option | Effect |
|---|---|
| **Keep 1.12.1 now (recommended for the first build)** | Matches the specification and the code as written. A debug APK installs and runs on normal 4 KB-page phones. Risk: Google Play will reject or flag a release if 64-bit libraries are not 16 KB-ready, and devices running 16 KB pages may refuse to load 4 KB-aligned native libraries. |
| Move to 1.13.1 or 1.14.0 **later, as a separate commit** | May produce 16 KB-aligned natives, but that is unproven for this setup. Needs: re-check API compatibility (small for Stage 2, as above), a fresh build, and the alignment report to prove the result. Do not mix 1.13.x versions. Changes the specification's pinned version, so it needs your decision. |
| Upgrade now | **Not recommended.** It would mix a toolchain change into the very first build, so any failure would be impossible to attribute. |

**Decision for you, after the first build succeeds:** read `elf-alignment-report.txt` first. If the 64-bit libraries show `16KB-OK`, no upgrade is needed. If not, we test 1.13.1 and 1.14.0 as isolated experiments and you decide whether to relax the "libGDX 1.12.1" requirement.

## 6. How to start the first cloud APK build

1. Sign in at <https://codemagic.io> with the GitHub account that can see `masjidcastel-netizen/My-Umrah-Journey`, and allow Codemagic to access that repository.
2. **Add application**, choose that repository, and when asked for the project type pick **Android** and the **`codemagic.yaml`** configuration (not the "Workflow Editor").
3. Open the app, choose **Start new build**, set **Branch** to `native-android-development` and **Workflow** to `android-debug` (Android debug APK), then start it.
4. Wait for the build (the first run downloads Gradle and all libraries and can take 10 to 25 minutes).
5. **If it succeeds**, download `app-debug.apk` from **Artifacts**, copy it to your phone, allow installs from that source and open **My Umrah Journey**. Also download `elf-alignment-report.txt` and the two `gradle-wrapper.*` artifacts.
6. **If it fails**, copy the first red error block (the lines starting `FAILURE:` / `What went wrong:` and the 20 lines above) or the whole log, and send it to me. I will fix errors one commit each.
7. After an install, run the 9 acceptance tests in `MyUmrahJourney/README.md` and tell me the phone model, Android version and results.

Menu names above are from my understanding of Codemagic's interface and may differ slightly; follow Codemagic's on-screen prompts where they differ.

Do **not** treat the Android project as building until step 5 happens with a real APK.
